# E1.42.3 本地只读容量诊断

本阶段为缺少可访问 MCP 主机时的设备验证路径。复用 E1.41/E1.42 的容量和 read/mmap 代码，从本体已有 USB 控制台输出结果；USB 结果只能证明设备执行结果，不证明云端工具可见性或权限已经解决。

## 实现边界

- 固件增量仅 `main/Kconfig.projbuild` 与 `main/boards/esp_vocat/dev_tools.cc`。
- `DESKBOT_FLASH_PROBE_BOOT_EXPORT` 默认关闭；诊断构建显式开启。
- 一个优先级 1、6144 B 栈的任务每秒观察一次状态：联网 `Idle` 状态，或稳定处于 Wi-Fi 配置状态至少 10 秒后，音频队列连续三次为空即导出一次；120 秒未达到条件则结束。连续观察不表示持有空闲锁；输出期间不保证用户不会开始对话。
- 任务不经 UI、LVGL、主事件循环或计时器回调执行，不注册命令输入、网络服务器或新的硬件控制工具。
- 每条 JSON 上限 8192 B，带类别及 UTF-8 字节长度。解析器拒绝截断、重复启动混合、错误 JSON、缺项和错误负载。
- 上下界读取、映射比较、越界拒绝、MMU 释放和堆快照继续由既有探针负责。导出后任务删除，串口无需输入任何应用命令。

## 构建与部署流程

1. 工具链预检及改动前源码快照留在本仓库 `tmp/e1423-serial-probe-20261102/`。
2. 使用锁定依赖、独立源码与构建目录；同目录依次构建关闭/启用两版。关闭版无诊断任务符号，启用版有；有效配置仅允许新增诊断开关。
3. 两版 bootloader、分区表、表情包、语音模型与 E1.42 逐字节比较；App 至少保留 1 MiB 余量。
4. 再确认 COM4 的设备身份；读出实际 App 擦除扇区供精确回退，核对当前 App/bootloader/分区表与已验收版本。
5. 仅刷 App `0x10000`，完整回读并核对 payload 和擦除尾部。禁止全片擦除，不写 bootloader、分区表、assets、model、NVS 或 C61。
6. 捕获真实启动与诊断记录，运行 `scripts/validate-expression-e1-42-3-serial.py`。原始启动日志留本机；公开报告不含 MAC、UUID、Wi-Fi 凭据等。
7. 启动成功与只读探针结果分别记录；点击/对话中切菜单/摸头/睡眠唤醒仍须用户实机确认。

## 2026-11-02 构建与离线复核

- 关闭/启用两版构建完成，报告为 `isolated_default_off_and_diagnostic_builds_passed`。当前源码逐文件摘要与构建报告再次核对一致；增量只包含上述两个固件文件。
- 关闭版 App 为 4,481,776 B；启用版为 4,482,832 B，增加 1,056 B。启用版 App 分区余量为 1,661,168 B。
- 两版 bootloader、分区表、表情包和语音模型均与 E1.42 相同；只有启用版包含一次性诊断任务符号。
- 容量专项 25/25 通过。前序完整离线套件为 407 项：402 通过、2 条件跳过、3 条旧 E1.26 快照检查失败。失败来自当前 Kconfig/DevTools 已包含后续增量，以及旧完整构建报告不再匹配当前源码清单。保留原检查和旧报告，不把该套件标为全绿，不以改写旧证据代替本阶段构建审计。
- COM4 在写前通过 USB VID/PID 与本地已确认序列号核对；身份细节仅保存在私有日志。

本轮首次写前门禁在资源摘要检查处停止，当时尚未调用写入命令。原因是本地部署脚本误将构建参考资源作为现场 E1.18 的基准。重新核对整个 `0x5EC000..0xBC8000` 后，现场资源 SHA-256 为 `d0858a38f9788dc4a57e4f7c2417425f0cf762ebe2268ea049d7d2feb65cada6`，与已验收 E1.40 现场备份和公开机器记录一致；独立模型区域也逐字节一致。保留失败日志，修正为“bootloader/分区表/App 对照构建锚点，assets 对照现场验收锚点”的双基准门禁后继续；没有重新打包或覆盖资源。

首次诊断启动已证明工具链和 COM4 可访问，但没有导出容量记录：Wi-Fi 未配置时设备进入 `kDeviceStateWifiConfiguring`，旧任务仅等待 `kDeviceStateIdle`，120 秒后按设计超时。这是触发条件不覆盖离线配网状态，并非用户权限不足。E1.42 已从原扇区备份精确恢复并回读，后续恢复启动日志确认原 App 正常启动。保留首轮失败日志，不把缺记录写成探针失败或串口权限错误。修正后的诊断构建采用上述稳定配网/空音频队列门槛；联网 `Idle` 和 UI/音频/主事件路径仍不被接管。

`device-step.py` 的 esptool 操作使用 `--after no_reset`，因此完成回读后设备仍可能停在下载模式。启动捕获应使用固定 IDF Python 3.11 调用 `tools/capture-body-boot.py --usb-reset`，先打开监听再进行 USB-Serial/JTAG 正常复位；此路径需要该环境的 `esptool.reset`。不要用 `--no-reset` 期待下载模式自动运行 App。恢复原 App 后也需要单独启动并采集日志。

`0x00FFFFF0` 的 32 B 样本跨越 16 MiB 边界；`0x01000000` 的 32 B 样本位于上半区。当前两处参考都是擦除态 `FF`：即使 direct read 与 mmap 相同，也不能单独排除地址别名，不能证明新资源已解码、动画已显示或 8 MiB 资源迁移已通过。

因此下阶段先制定上半区已知非 `FF` 数据的可回退验证：准备精确资源候选、写前范围备份、容量与对齐审计、直接读与 CPU mmap 内容摘要比较；先保留旧资源与旧分区表，后续再独立迁移活动资源。底座维修和客户端接入不与这次存储验证混在一起。

构建、设备执行和人工验收状态见后续结果记录；本页流程不替代真实执行证据。诊断串口只提供设备端 read/mmap JSON，不证明 MCP 主机看见或调用了工具；MCP 入口待目标主机可用时，另用 E1.42.2 捕获契约补齐，不扩权官方 user-only 工具。
