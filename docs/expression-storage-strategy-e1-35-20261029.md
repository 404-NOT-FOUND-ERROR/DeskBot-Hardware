# 表情资源存储策略与分区扩容可行性 / E1.35

> **2026-10-30 容量更正**：实机已确认是 N32R16，物理 Flash **32 MiB**、PSRAM **16 MiB**；本文及 E1.35a/b 的 8 MiB 资源候选只研究了当前 **16 MiB 软件配置**。本文所述 3.44 MiB / 1.30 MiB 尾部均限于该配置，不能作为整片容量结论。完整 32 MiB 已只读备份并独立校验，迁移尚未执行；下一步先重新规划 32 MiB 方案，详见 [硬件档案](hardware-profile-n32r16-20261029.md) 与 [E1.35c](expression-storage-migration-e1-35c-20261029.md)。下文保留当时的离线审计范围。

更新：2026-10-29。本文回应“动画资源空间有限、需要同时保留对称和非对称动画、是否应扩容分区”的新决策输入。当前只做离线审计和规划；没有修改固件源码、没有修改正式分区表、没有刷写设备。

## 结论

本篇保留 E1.35 决策时的初始布局证据；后续状态以 [E1.35a 扩容预检与未来空间](expression-storage-preflight-e1-35a-20261029.md) 为准。E1.35a 四份隔离构建、原 App 身份和分区/预算审计已通过；未访问设备，实机 mmap、迁移与启动回归仍待验证。[E1.35b 原资源迁移包与回退审计](expression-storage-migration-e1-35b-20261029.md) 也已完成，下一步先补现场身份和原始备份。

布局层面有扩容空间，应作为优先研究方案；但它不是把 `assets` 的容量数字改大后直接刷写。当前构建配置为 16 MB Flash，正式分区表末尾存在未分配空间，扩容可以在不压缩 App、NVS 或语音模型的前提下进行。首个研究目标建议把 `assets` 从 6,000 KiB（5.859375 MiB）扩到 8 MiB，同时把同样大小的 `model` 分区后移，保留 Flash 尾部余量。

扩容解决的是“设备可放入多少资源”，不能解决动画布局、镜像策略、循环时序和语义误用。资源库应采用“电脑保存完整母库，设备放当前所需的活动包”的模式；有意对称的动画可以使用单眼加镜像，非对称动画应保留完整画面，并单独验证非镜像的产品播放路径，不能为了省空间强行镜像。

对 E1.18 包的静态容量投影：

| 指标 | 当前 6,000 KiB | 候选 8 MiB |
| --- | ---: | ---: |
| 分区容量 | 6,144,000 B | 8,388,608 B |

## 为什么还不能直接刷

本体通过分区标签查找资源：`assets.cc` 使用 `assets` 标签，语音模型代码使用 `esp_srmodel_init("model")` 查找 `model` 标签，CMake 也从实际分区表取得 `assets` 的偏移和大小。因此源码结构上支持移动 `model` 和扩大 `assets`，不需要把地址硬编码进 UI 或播放器。

但 `esp_mmap_assets` 在启用 mmap 时按整个分区建立映射，而不是只映射当前包的有效字节；本构建使用 64 KiB MMU 页。当前 `assets` 起点 `0x5EC000` 没有 64 KiB 对齐，映射会按页向下对齐并向上取整：当前分区覆盖 95 页，8 MiB 候选覆盖 129 页。它们是地址范围的页数，不等于新的独占分配量；实际复用和可用地址空间取决于运行状态。组件检查 `free_pages * 65536 > partition_size`，随后仍须由实际 mmap 返回结果验证可用性；语音模型、代码和 PSRAM 等也会影响映射资源。不能只凭“Flash 还有空位”判断运行成功。

模型分区虽然只改变偏移，但仍必须完整搬移、回读并验证哈希。正式迁移还要保留：旧分区表、App、E1.18 `assets`、`model` 镜像、NVS 和恢复命令。分区迁移不是普通的 `0x10000` App-only 更新，也不能擦除 Flash 试错。

## 动画库的两层策略

### 电脑端母库

母库保存原始 GIF/PNG/设计稿、完整脸 EAF、单眼/镜像候选、角色草稿、许可证、帧数、循环范围、布局和 SHA-256。它可以保存设备不使用的历史资源，也可以保存多个角色版本；不受设备活动分区容量约束。

### 设备活动包

设备活动包保留核心系统资源、必要降级动画和已选角色资源；容得下时可以共享或预置多个角色，但不要求把整个母库装入设备。每次替换都生成一个精确包，完整旧包留在电脑供回滚；不把整套乐鑫示例 `.bin` 当作喵伴资源包导入。固定分区下删减成员不会减少整区 mmap 大小；包容量和映射容量分别核验。

资源筛选必须先按语义和调用关系处理，再按字节数处理：

- `eat.eaf` 用于底座小鱼配件反馈，E1.18 中为 435,957 B（约 426 KiB）。用户已明确本产品不用小鱼配件，可提出归档到电脑母库的候选；实际释放量还要重打包计算索引开销。删除 payload 前要处理全部已确认调用：为仍可能到达的接口提供布局兼容的回退，或明确禁用该产品入口，防止事件调用缺文件。
- `insert.eaf` 约 947,574 B，是本体接回/底座重连反馈，不是小鱼动画，必须保护。
- `Happy.eaf` 约 81,645 B，被 9 个语义共享；删除一个语义不会自动释放它，只有所有引用都迁移后才可讨论移除。
- `eye_anim` 的 `mirror:auto` 适合有意对称的单眼动画；`emerg_dlg` 等全画面对象是 `mirror:false`。非对称表情、文字、道具方向和左右不同动作必须保留完整脸或明确的非镜像布局。

镜像目前是 `layout.json` 的对象级配置，不是每条表情语义都可以自由切换的参数。不能为了一个完整脸候选把共享的 `eye_anim` 全局改为不镜像，也不能把临时对话叠层直接当作普通表情替代。扩容后，原完整脸候选依然要验证普通表情路径、圆屏构图与其他动画是否能共存。E1.34 发现的尾帧元数据和局部循环限制也不会因扩容自动消失。

因此“扩容 + 精选”不是二选一：扩容先提供安全余量，精选再把低价值或未使用资源归档，并把余量留给更生动的日常语义。删除资源不能只看名字或一次未观察到的日志，必须通过路由覆盖、共享引用、布局、播放器和回退检查。

## 后续开发闸门

1. **E1.35a 分区迁移离线预检**：本轮候选表的 ESP-IDF 生成、反向解析、边界和容量已通过。下一步核算 mmap 地址空间、核对模型加载和升级/回退脚本，产出独立迁移清单；复用已验收 App 和资源哈希，若需重构建只使用独立 build 目录，任何 App 差异都必须解释。正式 CSV 仍不变。
2. **E1.35b 原资源迁移候选**：只使用当前 E1.18 包和原模型内容，逐成员验证资源与语义不变；整理旧/新布局及完整回退。先隔离“分区变化”，此阶段不移除 `eat.eaf`，不把新动画一起带入。
3. **E1.35c 授权后的实机迁移与用户回归**：重新识别本体与实际 Flash，备份旧分区表、App、assets、model、NVS 及受影响尾部。迁移清单须规定保持下载模式、模型复制与校验、资源覆盖范围、分区表提交时机，以及中断后的 USB 恢复顺序；不能从本文直接生成通用写入命令。回读全部变更范围并核对未改分区，确认整区 mmap/资源挂载及语音模型加载成功，再验收对话/菜单、触摸、睡眠/唤醒。App-only 回退不能恢复分区布局。
4. **E1.35d 精选活动包与播放器适配**：存储布局实机稳定后，单独提出小鱼资源归档；在母库保留它，处理入口/共享引用与回退，再选一个日常语义。对称/非对称构图、188 帧完整调度、循环/停止、许可、实际包大小和节点前后预览全部核验；一次只改变一个可验收变量，所需运行时布局扩展另立最小增量。
5. **E1.35e 最小资源部署**：视觉选择与离线闸门通过后，按新的分区版本生成候选和精确回退；独立授权、写入、回读并验收。所有工具须拒绝把旧布局镜像或写入命令误用于新布局。
6. 角色 profile 复用已验证资产目录和布局能力，客户端以后负责角色绑定和表达调度。底座维修后的外壳识别、只读身体事实出口、最后的 DeepSeek/TTS 替换继续按原路线进行。

E1.35 初始审计只通过布局可行性。现已由 E1.35a 补齐四份隔离构建和模型/MMU 源码预检；实机 mmap 和写入仍未尝试。设备以此前验收的 E1.26 App + E1.18 assets 为基线，本轮没有重新读取它。
