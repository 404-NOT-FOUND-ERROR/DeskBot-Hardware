# E3f-9d.2：全屏错行排查

2026-11-12。当前 E3f-9d.1 双角色验收发现：表情和菜单均花屏，画面缓慢由上到下更新；触摸与其他操作仍可用。照片保留在本轮记录。双角色画面验收待修复后继续。

## 排查顺序

1. 保存当前工作台快照，交接唯一串口所有者，保持 DTR/RTS 关闭采集原日志。
2. 检查像素发送、DMA 分配、显示超时和内部内存，复核实际构建中的显示补丁。
3. 按证据选择小范围软件修正或已验收版本对照；每次保持资源与 App 的配套关系，保留现场 NVS 和恢复材料。
4. 通过离线测试、构建和独立 AI 复核后再安装候选，由主人观察屏幕，再测菜单与对话。

数据流：工作台/串口证据 → 实际固件与驱动 → 发送路径和资源统计 → 单项候选或基线对照。诊断接口复用现有本机 HTTP、串口日志和安装恢复工具；新显示接口在证据明确后定义。

当前快照：主页待机，内部空闲约 16 KiB、历史最低约 9 KiB；角色查询和目录读取未完成。该内存读数是排查线索。硬件连接、QSPI 传输和软件内存/队列路径通过后续对照区分。

S1a/S1b 离线成果已归档；当前先处理显示问题，再验收双角色，之后进入固定外壳采集。

## 日志结论与候选

原始日志在保持故障现场的 40 秒内，持续记录 `Failed to allocate priv TX buffer`、像素排队失败和 `ESP_ERR_NO_MEM`。内部 DMA 副本申请失败使部分像素未发送，能解释残留和逐层刷新。角色常驻数据已放在 PSRAM；当前证据指向共用发送路径的内部内存压力。

E3f-9d.2 只调整板级 `io_config.flags.psram_dma_direct = true`。接口、40 MHz QSPI、4,092 B 上限、队列深度 2、菜单补丁和首帧处理保持当前实现。ESP-IDF 5.5.5 的 S3 路径直接发送 PSRAM 像素；触发对齐修复时，副本仍从 PSRAM 申请，并在事务回收后释放。内部像素仍沿用原路径。资源包与 NVS 继续沿用当前内容。

数据流：菜单/LVGL 或表情/GFX → ST77916 → LCD IO 分块 → PSRAM DMA → 屏幕；原完成回调决定源缓冲何时可复用。依赖固定为当前 E3f-9d.1 源码、已有组件锁及 IDF 5.5.5。

验证分三层：原生夹具提取真实 IDF 分配和 LCD IO 函数，在内部申请失败时检查外部发送、未对齐尾块、逐字节内容、队列回收与失败恢复；构建检查唯一源码差异及受保护产物；安装后保存原始日志，检查内存错误与 `DMA TX underflow`，再观察两个角色、菜单和对话。80 MHz 八线 PSRAM 为 40 MHz 四线 QSPI 提供带宽基础，并发表现由实机验证。

40 秒原始采集中，内部 TX 申请失败 1,590 次，像素发送和刷新失败各 1,605 次；内部空闲约 16 KiB、历史最低 8,988 B。照片、原始字节和统计保存在 `tmp/display-corruption-e3f9d2-20261112/`，统计见 `diagnosis.json`。

2026-11-13 连接检查：COM4 当前未枚举；COM13/COM14 正由其他调试程序使用。本轮先完成离线候选与恢复准备，头部接回后核对设备身份，再安装和观察。

## 补充：开机黑屏与开屏残留

2026-11-13 主人补充早期已有的现象：插着 USB 操作电源开关，有时背光亮、整屏黑，但仍能说话；多次开关后恢复。成功开屏时可能先出现雪花，随后新内容覆盖到哪里，哪里就恢复正常。触摸响应尚未确认。

判断：主程序能够运行，黑屏优先查屏幕复位、初始化与供电时序；按区域覆盖后恢复符合首屏未完整写入的表现。USB 是否使部分电路持续供电，要结合实际电源电路确认。运行中 DMA 内存错误已有原始日志；这两种启动现象单独验证。

源码线索：板级复位、初始化和开屏调用未检查返回结果；GFX 先于 LVGL 显示适配器启动，适配器未就绪时刷新回调会跳过发送并通知完成。GFX 已有启动全屏刷新，因此后续要核对这次刷新是否真正送达；“未清屏”与“首次刷新被跳过或失败”分别验证。

接续：先安装已封存 E3f-9d.2，观察运行中发送错误和画面；再比较完全断电开机、USB 保持连接时开关、软件重启，记录屏幕复位、初始化结果和首个完整刷新完成。根据结果处理初始化检查、显示就绪后的全屏底色和背光时序，随后回归菜单、对话、角色与睡眠。启动观察可补一段从开关电源到主页的视频，串口日志同步保存。

## 实机结果：E3f-9d.2 未通过显示检查

2026-11-13 已在 COM4 安装候选，App 完整回读、其余 Flash、NVS 与启动身份均一致。45 秒启动日志中，内部 TX 分配失败和 `ESP_ERR_NO_MEM` 均为 0；启动约 640 ms 出现一次 `DMA TX underflow`，接着事务回收失败及刷新 `ESP_ERR_INVALID_STATE`。显示检查未通过，已使用同轮备份恢复 E3f-9d.1；原 App 逐字节回读、其余静态区、NVS 和启动身份均通过。结果见 `artifacts/display-psram-e3f9d2/live-result.json`。

IDF 在这类错误后可能保留错误的在途计数，接续对照使用重新启动后的独立版本。下一候选按 [E3f-9d.3 设计](display-clock-e3f9d3.md)只降低 QSPI 时钟，并在安装启动检查中加入显示错误判定。
