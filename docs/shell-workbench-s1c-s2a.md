# 外壳工作台：登记准备与角色绑定

更新：2026-11-13。沿用已验收 E3f-9d.3 和双角色包。本轮完成 S1c、S2a 的电脑端；正式拆装采样由主人回来后进行。

## 两步交付

1. **S1c 登记准备**：填写传感器、安装基准与外壳名称，生成登记和独立拆装任务。导入每次静止采集的原日志后，复用 S1a 评估、S1b 保存档案。进度可保存、重新打开。
2. **S2a 角色绑定预演**：外壳选择对应角色，绑定随电脑项目保存。用已登记档案重新识别独立记录，展示“磁场 → 外壳 → 角色 → 切换接口”；分别演练已知、取下和未知状态。

正式项目记录主人确认的外壳名称和安装基准；采集、导入和评估由开发者操作，主人按提示拆装。历史滑块示例单列为演练，保留原始标签和采样覆盖。

## 接口和数据流

| 接口 | 用途 |
| --- | --- |
| `GET /api/shells/state?session_id=…` | 项目列表、任务、绑定和最近评估 |
| `POST /api/shells/create` | 创建采集项目；传入名称、设备编号、context、外壳名称 |
| `POST /api/shells/import` | 按任务导入带时间的 COM4 原日志，核对独立装配编号 |
| `POST /api/shells/evaluate` | 生成 S1a 清单、评估和 S1b 档案 |
| `POST /api/shells/bind` | 保存外壳对应的角色；核对项目版本 |
| `POST /api/shells/rehearse` | 用保存档案重播，返回角色解析和已有启用操作的预览 |
| `POST /api/shells/example` | 导入一份清楚标记的历史演练项目 |

数据流：独立原日志 → M2 解码/识别 → S1a 评估 → S1b 档案 → 外壳与角色绑定 → 启用操作预演。工作台新增“外壳”入口，沿用现有界面与角色名称。

依赖为 Python 标准库、现有磁场模块和工作台 HTTP 服务。项目保存在 `tmp/deskbot-shell-workbench/`；日志只新增，项目文件原子保存，更新核对版本。每份日志最多 8 MiB，每项目最多 100 份、合计 64 MiB；每个静止窗口至少 10 秒。登记与评估使用不同装配、时间和样本。

S2a 保存的是已安装表达角色的绑定草稿，字段沿用 `device_id / shell_id / magnet_profile_id / role_id`。磁档案的 payload 摘要固定登记版本，角色图摘要固定资源版本。既有完整人格档案和 E1.6 人工确认协议继续用于后续客户端；本轮不填造人格、音色或旧版 release lock。

## 验证与接续

验证通过：21 项工作台测试及 S1a/S1b 的 55 项回归；15 项浏览器检查，包含多标签冲突恢复与三种窗口宽度。历史真实日志经过生产识别器、档案加载及绑定预演，整条浏览器测试发送的设备命令为 0。另一 AI 独立复测 76 项通过，并完成源码、生成页和启动参数复核。

启动：`scripts/start-deskbot-shell-workbench.ps1`，默认端口 8779。使用既有 Python 3.13 和 IDF Python，先生成页面，再启动工作台服务。原角色编辑、预览和设备连接入口继续保留。

本轮用 `scripts/start-deskbot-shell-workbench.ps1 -Preview` 开放 [8780/#shells](http://127.0.0.1:8780/#shells) 电脑端预览；角色状态单独保存，8779 保持原设备连接。开始实机采集时，再交接串口到新版工作台。

实现与归档：`protocol/shell_workbench.py`、`shell_role_assignment.py` 和 `shell_workbench_http.py`；源码、测试、界面截图和复核结果汇总于 `artifacts/shell-workbench-s1c-s2a-20261113/`。独立复核已落实多标签冲突后自动重读、保存后控件恢复和正式/历史数据文案区分。相同采样重评保持档案版本稳定。

接续：正式外壳采集与重复识别 → 主人确认绑定 → 实时自动切换 → 人格与声音。实测时使用已经验收的 App，先完成一套外壳，再补第二套和未知对照。
