# 安装同步运行接入

目标：工作台确认安装、设备显示并保存后，自动把同一记录同步到运行客户端，卡片显示客户端接收结果。延续原个体和 SQLite 存档。

## 接口与数据流

`原安装服务 → 自动同步任务 → 客户端安装接收器 → 原 SQLite → 接收凭证 → 安装卡片`。

| 部分 | 实现 |
| --- | --- |
| 客户端启动 | 原启动器组合 `receiver.mjs`，共用原持久层与设备登记；新增来源编号参数 |
| 工作台启动 | 共享连接启动器传入客户端地址、固定来源编号、个体与设备，创建单一同步任务 |
| 自动同步 | 每 2 秒读取当前安装；已保存且设备结果匹配时提交，回应丢失沿原编号重试 |
| 状态查询 | 原 `GET /api/shell-installation/state` 增加 `client_sync`，包含状态、安装编号、接收时间和原因 |
| 持久恢复 | 独立小型状态文件保存来源、身份和最近凭证；重开后向客户端核对原凭证 |

接收沿用 `POST /api/hardware/installations`，恢复核对沿用 `GET /api/hardware/installation`。来源编号固定对应当前安装库；同一路径只运行一个同步任务。任务只同步记录，设备请求与原输出队列由既有模块处理。

## 状态与边界

- 确认中、设备未保存、当前目标变化时显示等待；同步成功关联当前安装编号。
- 客户端暂时不可达时保留安装结果和凭证，后台重试。请求失败与已接收分别显示。
- 相同安装的设备查询序号变化沿用原凭证；新的安装编号按原修订排序。
- 显示“客户端已同步”前核对安装摘要、来源、个体和设备。客户端重开后重新查询，避免仅凭电脑缓存显示成功。
- 卡片在当前安装切换后立即显示新目标进度；旧安装的接收结果保留原归属。
- 本轮接通安装事实。聊天与音色采用配置接续下一轮，空配置沿用现有设置。

同步任务以状态文件锁独占，固定来源、个体、设备、客户端地址与安装库路径，配置不同时报冲突。一次只运行一个检查；完成后隔 2 秒再执行。网络请求在安装与设备锁外进行，每次请求前后重读当前编号和安装摘要；旧请求的凭证保留原归属。

`client_sync` 分开显示历史凭证、当前核验时间和是否已核验。同步成功后查询客户端当前记录再次核对；不可达或重开尚未核对时显示待同步。关闭先停止并等待在途任务，再释放状态文件锁。

## 依赖、测试与上线

沿用原客户端启动器、`ShellInstallation`、共享 USB 连接和已验收同步接收器。Python 与 Node 使用已核对的绝对路径，新增代码使用标准库。

单元覆盖自动同步、等待、重复、回执丢失、慢请求期间目标更新、客户端暂时离线、任务重开、双实例和关闭顺序。集成使用原 HTTP／SQLite、生产安装服务与内存 ControlLink，检查 A→B→A、客户端存档更换与恢复、旧启动器继续读取新增同步记录后的数据库；浏览器检查状态、连续确认及表单保留。

上线先用 SQLite 在线 backup 创建一致快照，保留旧启动器、页面和配置。只重开客户端与共享工作台，使用原端口、原存档和原设备所有者；核对当前 B 记录同步、原生活记录、输出队列、USB 会话和重复接收。回退恢复旧启动器与页面，沿用当前数据库，保留期间新增的生活与队列记录；数据库快照另用于明确范围的数据恢复。设计与实现由另一 AI 复核，结果归档后更新主线。

63 项 Python、23 项 Node、19 项浏览器检查通过。原 SQLite 在线备份的副本通过新服务接收、重开恢复与原启动器回退检查。现场原有 856 条记录全部保留，生活档案和六组交流结果一致；新增世界记录来自原时钟推进。USB 所有者、启动与会话保持连续。

本轮部署后的再次重开操作被自动审批策略拦截，现场服务继续运行。重开与回退结果来自隔离备份副本。测试、运行核对、源码和独立复核见[交付归档](../artifacts/client-installation-runtime-20261117-r3/delivery.json)。
